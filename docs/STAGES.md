# The nine DevSecOps stages, job by job

![The nine stages with the CI jobs that touch each one](media/diagrams/stages.png)

Every row below names something you can open in this repository or in the GitLab project. **Job names are spelled exactly as in [`.gitlab-ci.yml`](../.gitlab-ci.yml)** or in the release child pipeline that [`probation/src/cli/release-plan.ts`](../probation/src/cli/release-plan.ts) generates. Template jobs (SAST, Secret Detection, Dependency Scanning) take their names from GitLab's templates.

Pipelines that exist:

- **Merge request pipeline:** `verify:check`, `verify:replay`, the security templates and `secure:npm-audit`, `measure:sci`, then `probation:gate`.
- **Main pipeline:** the same verify, secure and measure jobs, then `package:image`, `release:plan`, `release:run` (the child pipeline), `govern:baseline`, `govern:release-notes` and `pages`.
- **Release child pipeline**, generated per merge: `deploy:staging` → `approve:production` → `deploy:canary` → the soak (`soak:canary` in parallel with `soak:canary-logs` → `soak:canary-signal`) → `promote:production`, or `rollback:soak` and `rollback:production` → `settle:survived` or `settle:rolled-back`. The settle jobs exist only when the merged MR was Undertaker's.
- **Scheduled pipeline (nightly):** `census:collect` → `census:file` → `undertaker:dig` and `probation:sweep` → `pages`.
- **Tag pipeline (`catalog-*` tags only):** `catalog-sync`, from GitLab's `components/ai-catalog/catalog-sync` CI component, publishes `flows/*.yml` and `agents/*.yml` to the AI Catalog. The same component's `validate-items` job checks them in the verify stage of the other pipelines.

## Stage table

| Stage | Exact jobs and files | What the judge sees | Screenshot as evidence |
|---|---|---|---|
| **Plan** | `census:collect` (reads Cloud Run request logs with `gcloud logging read`), `census:file` (`probation/src/cli/census.ts` → `probation/src/census.ts`), `undertaker:dig` (`probation/src/cli/start-flow.ts` → `probation/src/dig.ts`) | Production traffic turned into a work queue. One issue per zero-traffic route, never-flipped flag, unused dependency or orphan export, labelled `undertaker::candidate`, `zone::*` and `kind::*`, with request counts and the census window in the body. `undertaker:dig` picks one, labels it `undertaker::in-progress` and notes the flow ID on it. | The issue list filtered by `undertaker::candidate`; one candidate issue body; the `census:file` job log. |
| **Create** | The **Undertaker** flow, [`flows/undertaker.yml`](../flows/undertaker.yml): three `AgentComponent`s, `exhume` → `bury` → `coroner`, with `coding_environment: none` (API tools only). The Undertaker flow is started by `undertaker:dig` through the Flows API. A second, foundational flow covers the failure path: a *Pipeline failed* flow trigger starts GitLab's Fix CI/CD Pipeline flow, which runs in the environment defined by `.gitlab/duo/agent-config.yml`. ✏️ Screenshot the trigger once it is configured in the project. | An agent that can only delete. It opens one deletion MR: an epitaph, the census evidence, the file list and `Closes #n`. Then its own `coroner` step posts a "Coroner's report" and adds `coroner::objection` if it finds a live reference. | The Undertaker flow session in GitLab (its agent session log); the MR description with the epitaph; the Coroner's report note. |
| **Verify** | `verify:check` (Biome lint, `tsc`, Vitest with a JUnit report), `verify:replay` (`probation/src/cli/replay.ts`: every route that served production traffic in the census window must still answer), `validate-items` (the flow and agent YAML against the AI Catalog schemas) | Ordinary tests plus a check built from production traffic. A deletion that removes a route real clients used fails here, before any human looks at it. | MR pipeline graph; the MR's test report widget; the `verify:replay` job log. |
| **Package** | `package:image` (Cloud Build → Artifact Registry, one image tagged with `$CI_COMMIT_SHA`). `catalog-sync` (on `catalog-*` tags) publishes the Undertaker flow and the Probation Clerk agent to the AI Catalog. | One immutable image per commit, which is exactly what staging, canary and rollback move traffic between. The agent and the flow ship as versioned catalog items, not as settings typed into a UI. | Artifact Registry image list; the `package:image` log; the `catalog-sync` tag pipeline; the AI Catalog entries. |
| **Secure** | `include: template: Jobs/SAST.gitlab-ci.yml`, `Jobs/Secret-Detection.gitlab-ci.yml`, `Jobs/Dependency-Scanning.gitlab-ci.yml` (with `AST_ENABLE_MR_PIPELINES: "true"`); `secure:npm-audit` (`probation/src/cli/audit.ts`) writes `gl-npm-audit-report.json`; `probation:gate` diffs findings against main's baseline (`probation/src/security.ts`). The agent's auth and CI zones are `forbidden` in `probation/policy.yml`. | Security is part of the trust score: an MR that introduces a new finding is blocked and its zones lose 30 points. Any file under `app/src/auth/**`, `probation/**`, `flows/**`, `agents/**`, `mcp/**`, `ci/**`, `infra/**`, `.gitlab/**` or `.gitlab-ci.yml` blocks the MR, whatever the score. | MR security widget; the gate note on a blocked MR. |
| **Release** | `release:plan` writes `.out/release.yml`; `release:run` triggers it as a child pipeline (`resource_group: production`). The child holds `deploy:staging`, `approve:production` (manual at Assisted and Supervised, automatic at Hands-off), `deploy:canary`, `promote:production`. `govern:release-notes` creates a GitLab Release `release-<pipeline iid>`. | The release pipeline is shaped by the trust the agent has earned. At Supervised it stops at a play button; at Hands-off it runs from merge to production with no human. | The child pipeline graph at Supervised (manual job) next to one at Hands-off (no manual job); Deploy → Releases. |
| **Configure** | [`ci/deploy.sh`](../ci/deploy.sh) (`staging`, `canary`, `promote`, `rollback`): Cloud Run revision tags `rc-<sha>`, traffic splits, feature-flag env vars per revision, the API key from Secret Manager, 256 MiB and scale to zero. [`ci/gcp-auth.sh`](../ci/gcp-auth.sh) and [`infra/gcp-bootstrap.sh`](../infra/gcp-bootstrap.sh): keyless GitLab → GCP auth with Workload Identity Federation. [`probation/policy.yml`](../probation/policy.yml): zones, thresholds, scoring, soak and census settings. `npm run gitlab:setup` ([`scripts/gitlab-setup.ts`](../scripts/gitlab-setup.ts)) creates the project's labels, census schedule, `catalog-*` protected tag and MR settings idempotently; `npm run doctor` checks them read-only. | All production configuration changes come from CI, per revision, and can be traced to a commit. Autonomy itself is configuration: one YAML file that only humans may change. | Cloud Run → Revisions with tags and traffic percentages; `policy.yml`; the `GCP_WIF_*` variables (values hidden). |
| **Monitor** | Tallybook writes one structured `census` line per request to Cloud Logging (read by `census:collect`). `soak:canary` (`probation/src/cli/soak.ts`) hits the canary with [`probation/synthetics.yml`](../probation/synthetics.yml) for `soak.minutes` (3) and fails on any non-2xx. In parallel, `soak:canary-logs` reads the canary revision's census lines (and the previous revision's over the same window) and `soak:canary-signal` (`probation/src/soak-signal.ts`) fails on a 5xx rate above `soak.max_5xx_rate` or on 404s to unmatched routes above the baseline; a logging outage is a warning, never a rollback. `rollback:soak` takes traffic off the canary as soon as a synthetic fails; `rollback:production` runs `when: on_failure`. `measure:sci` measures energy per 1,000 requests on every pipeline. | Production is watched in three ways: the census for what is dead, the synthetics for known clients, and the canary's own traffic for everyone else. In the demo, the monthly partner export returns 404 on the canary and the rollback runs automatically. | `soak:canary` log showing `bookkeeping-partner-monthly-export → 404`; the `soak:canary-signal` log; `rollback:soak` and `rollback:production` logs; Cloud Run traffic back on the previous revision; the 🌱 SCI note on an MR. |
| **Govern** | `probation:gate` (`probation/src/gate.ts`, no LLM: least-trusted zone decides; sets auto-merge or waits), `settle:survived` / `settle:rolled-back` (`probation/src/cli/settle.ts`: score, promotion and demotion issues, revert, `undertaker::do-not-bury`), `probation:sweep` (−20 for closed-unmerged Undertaker MRs), `govern:baseline` (security and SCI baselines after a release), `pages` (the Probation Board and its ledger replay, `replay.html`). [`.gitlab/CODEOWNERS`](../.gitlab/CODEOWNERS) protects the policy and CI. Every score change is appended to `audit.jsonl` on the `ledger` branch. The **Probation Clerk** ([`agents/probation-clerk.yml`](../agents/probation-clerk.yml), a read-only custom Duo agent) answers "why is this zone Assisted?" in Duo Chat from `policy.yml` and the ledger branch. The **probation MCP server** ([`mcp/probation-server.ts`](../mcp/probation-server.ts), wired in [`.gitlab/duo/mcp.json`](../.gitlab/duo/mcp.json)) gives Duo Agentic Chat in the IDE the same answers. | Trust is earned, lost and audited in the open. The agent cannot change its own leash, and every level change has an issue, an MR and a pipeline behind it. | Gate note on an MR at each level; a 🎖️ promotion issue and a ⬇️ demotion issue; the `ledger` branch's `audit.jsonl`; the Probation Board and `replay.html`; a Clerk answer in Duo Chat. |

## Where each stage happens in the demo

| Act | What happens | Stages it shows |
|---|---|---|
| 1 · Assisted | Census files candidates, Undertaker opens an MR, a human merges, the canary survives, +10 | Plan, Create, Verify, Secure, Package, Release, Configure, Monitor, Govern |
| 2 · Supervised | Auto-merge; a human clicks `approve:production` | Release, Govern |
| 3 · Hands-off | Issue to production with no human | Release, Govern |
| 4 · Demotion | The soak catches a 404; rollback, revert, −40, do-not-bury | Monitor, Configure, Govern |

## Not covered, on purpose

- **CI minutes are not in the SCI.** They are a real saving from smaller dependency trees, but we did not measure them. See [`SCI.md`](SCI.md).
- **Latency and Cloud Monitoring metrics** are not in the soak. It judges the canary on synthetics and on its own request logs (5xx rate and deleted-route hits), which is what catches the client the census cannot see.
